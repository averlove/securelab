# F-02: Відсутність user-scoped обмеження частоти запитів на пошук інцидентів

- **Статус:** Fixed
- **Актив:** Доступність API та ресурси PostgreSQL під час виконання пошукових запитів `/api/incidents`
- **Компонент:** `src/SecureLab.Api/Program.cs`, `src/SecureLab.Api/Presentation/Endpoints/IncidentEndpoints.cs`
- **Пріоритет:** P2 (Impact: Medium × Likelihood: High)
- **Сценарій регресії:** `R-01` (перевірка політики `search-per-user`)

## Передумови і межі огляду
- **Review-start commit:** `b2234fb5cf5ad69b847304de3625f020b7a53d1c`
- **Середовище:** Windows 10, .NET SDK `10.0.302`, локальний HTTP-стенд `http://localhost:5080`, PostgreSQL (`127.0.0.1:54329`)
- **Тестові акаунти:** `alice` (`Reporter`), `bob` (`Reporter`)
- **Reset-команда:** `dotnet run --project src/SecureLab.Api -- --reset-database`
- **Маршрут:** `GET /api/incidents`
- **Виключення:** Лічильники зберігаються в пам'яті одного процесу API (`PartitionedRateLimiter`).

## Відтворення
1. Запустити `SecureLab.Api` без політики `search-per-user` та автентифікуватися під користувачем `alice`.
2. Виконати серію пошукових запитів `GET /api/incidents?q=incident` понад встановлену квоту пошуку (`RateLimiting:SearchPermitLimit`).
3. **Expected:** Перевищення квоти для конкретного користувача блокується статусом `429 Too Many Requests` без впливу на інших користувачів.
4. **Actual (до виправлення):** Окремий пер-користувацький ліміт на пошук був відсутній; запити одного користувача обмежувалися лише загальним лімітером по IP, що дозволяло одному акаунту створювати надмірне навантаження на БД або вичерпувати спільну IP-квоту для інших користувачів за тим самим NAT/проксі.

## Вплив і ймовірність
- **Статус перевірки:** спостережено локально.
- **Impact (Medium):** Деградація продуктивності БД при інтенсивному пошуку або блокування легітимних користувачів за спільною IP-адресою (noisy neighbor).
- **Likelihood (High):** Будь-який автентифікований користувач (`Reporter`) має доступ до `GET /api/incidents` і може автоматизувати часті запити.

## Першопричина
У `src/SecureLab.Api/Program.cs` використовувався лише `GlobalLimiter` із ключем партиціонування `RemoteIpAddress`, без виділеної політики rate limiting на рівні ідентифікатора автентифікованого користувача для пошукового маршруту.

## Виправлення
- У `src/SecureLab.Api/Program.cs` додано політику `search-per-user` (`PartitionedRateLimiter.GetFixedWindowLimiter`), де ключем партиціонування є `httpContext.User.Identity?.Name ?? "anonymous"`, ліміт задається параметром `RateLimiting:SearchPermitLimit` (за замовчуванням `10` запитів на `30` секунд, `QueueLimit = 0`), а код відхилення встановлено у `429 Too Many Requests`.
- Застосовано `.RequireRateLimiting("search-per-user")` до маршруту `GET /api/incidents`.
- **Чому усуває причину:** Кожен автентифікований користувач отримує ізольовану квоту на пошукові запити незалежно від інших користувачів.

## Retest
- Автентифіковано користувача `alice` та надіслано серію запитів `GET /api/incidents` понад `SearchPermitLimit`.
- **Фактичний результат:** Після вичерпання квоти запити `alice` відхилено зі статусом `429 Too Many Requests` (`ProblemDetails`).

## Positive regression
- Одразу після отримання `429` для `alice` виконано автентифікований запит `GET /api/incidents` від імені іншого користувача `bob`.
- **Фактичний результат:** Запит `bob` виконався успішно зі статусом `200 OK` та повернув список доступних інцидентів.

## Залишковий ризик
При горизонтальному масштабуванні на кілька екземплярів API in-memory лічильники не синхронізуються між інстансами (усувається у рамках розширення з розподіленим сховищем Redis).

## Доказ
- **Сценарій регресії:** `R-01`
- **Параметри:** `RateLimiting:SearchPermitLimit`, маршрут `GET /api/incidents`, акаунти `alice` (`429`) та `bob` (`200`).
